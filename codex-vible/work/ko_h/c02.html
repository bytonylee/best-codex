1부: 먼저 Codex가 무엇인지 이해하기

Codex 기본 이해

Codex는 대체 무엇인가

많은 사람은 Codex를 처음 들으면 자연스럽게 “또 하나의 AI 코드 작성 도구”라고 이해합니다.

하지만 Codex를 “코드 작성을 도와주는 ChatGPT” 정도로만 보면 그 가치를 쉽게 과소평가하게 됩니다.

Codex에서 정말 중요한 점은 함수 하나를 작성할 수 있는지, 코드 한 조각을 보완할 수 있는지, 오류 메시지를 설명할 수 있는지가 아닙니다. Codex는 AI 프로그래밍 도구의 역할이 바뀌고 있음을 보여줍니다.

예전의 AI는 옆에 앉아 코드 완성을 도와주는 사람이었습니다.

그다음의 AI는 에디터 안에서 함께 코드를 고치는 사람이었습니다.

지금의 Codex는 작업을 맡길 수 있는 엔지니어링 실행자에 더 가깝습니다.

Codex는 “이 코드를 어떻게 작성하나요?”에 답하는 데 그치지 않습니다. 프로젝트에 들어가 파일을 읽고, 컨텍스트를 이해하고, 계획을 세우고, 코드를 수정하고, 명령을 실행하고, 결과를 확인한 뒤, 마지막에는 review할 수 있는 결과로 변경 사항을 정리합니다.

이것이 Codex와 일반 AI 채팅 도구의 가장 큰 차이입니다.

5년 동안 네 번 바뀌었습니다

AI 프로그래밍 도구의 네 차례 진화

지난 몇 년 동안 AI 프로그래밍 도구는 대체로 네 단계를 거쳤습니다.

2021년: Copilot 자동 완성 시대. Codex라는 이름이 많은 개발자에게 처음 널리 알려진 계기는 GitHub Copilot이었습니다. 당시 AI의 주된 역할은 코드 자동 완성이었습니다. 앞부분을 쓰면 뒤를 채워 주고, 함수명을 쓰면 함수 본문을 채워 주었습니다. 더 똑똑한 입력기처럼 코드를 더 빠르게 쓰게 해 주었지만, 프로젝트를 어떻게 나누고, 파일을 어떻게 찾고, 테스트를 어떻게 실행할지는 여전히 주로 사람이 처리했습니다.

2022년: ChatGPT 대화 시대. ChatGPT가 등장한 뒤 AI 프로그래밍은 “자동 완성”에서 “대화”로 넘어갔습니다. 오류의 원인, 코드 최적화, API 작성법, 프로젝트 구조 설명을 직접 물어볼 수 있게 되었습니다. AI는 입력기에서 Q&A 파트너로 바뀌었습니다. 하지만 보통 실제 프로젝트 안에 있지는 않았습니다. 코드를 복사하고, 오류를 붙여 넣고, 컨텍스트를 직접 보충한 뒤, 답변을 다시 프로젝트로 옮겨야 했습니다.

2023–2024년: Cursor 프로젝트 협업 시대. Cursor 같은 AI 에디터는 AI를 실제로 에디터 안으로 들여왔습니다. 파일을 보고, 함수를 수정하고, 여러 파일에 걸쳐 리팩터링하고, 프로젝트 컨텍스트를 바탕으로 개발 작업의 일부를 완료할 수 있게 되었습니다. AI는 “질문에 답하기”에서 “프로젝트 수정을 돕기”로 바뀌기 시작했습니다. 하지만 대부분의 경우 여전히 IDE에 붙어 있었습니다. 사용자는 여전히 수정 과정을 지켜보고, 다음 단계를 판단하고, 테스트를 실행하고, 커밋을 정리해야 했습니다.

2025년: Codex 엔지니어링 Agent 시대. Codex가 다시 등장했을 때, 더 이상 과거의 코드 자동 완성 모델에 머물지 않았습니다. 실제 소프트웨어 엔지니어링 작업을 위한 coding agent가 되었습니다. 프로젝트를 읽고, 코드를 설명하고, bug를 수정하고, 기능을 추가하고, 테스트를 보완하고, 모듈을 리팩터링하고, 명령을 실행하고, diff를 확인하고, PR 설명을 정리하며, 여러 엔지니어링 작업을 병렬로 처리할 수도 있습니다.

이는 AI 프로그래밍 도구의 중심이 “코드 작성을 도와주기”에서 “작업 전달을 도와주기”로 이동하고 있음을 뜻합니다.

한 문장으로 정리하면 다음과 같습니다.

Copilot은 코드 완성을 도와주고, ChatGPT는 코드를 생각하도록 도와주고, Cursor는 프로젝트 수정을 함께하며, Codex는 엔지니어링 작업 실행을 도와주기 시작했습니다.

Codex로 할 수 있는 일

Codex로 할 수 있는 일

많은 사람이 Codex를 처음 사용할 때 바로 이렇게 묻습니다.

  • “로그인 페이지를 만들어 줘.”
  • “이 bug 좀 고쳐 줘.”
  • “프로젝트 하나 만들어 줘.”

물론 이런 것도 가능합니다. 하지만 충분히 정확한 요청은 아닙니다.

Codex가 정말 잘하는 일은 아무것도 없는 상태에서 코드 한 조각을 만드는 것이 아니라, 실제 프로젝트 안에서 일련의 엔지니어링 작업을 끝내는 것입니다.

프로젝트를 읽고, 파일을 찾고, 컨텍스트를 이해하고, 계획을 세우고, 코드를 수정하고, 명령을 실행하고, 결과를 확인하고, diff를 정리한 뒤, 마지막에는 작업을 review 가능한 상태까지 진행합니다.

따라서 Codex를 “코드 생성 버튼”으로 보지 마십시오.

더 정확히 말하면 다음과 같습니다.

Codex는 프로젝트 현장에 들어갈 수 있는 AI 엔지니어링 어시스턴트입니다.

Codex가 할 수 있는 일은 대략 다음 몇 가지로 나눌 수 있습니다.

낯선 프로젝트 이해하기

Codex 사용의 첫 단계는 바로 코드를 작성하게 하는 것이 아니라, 먼저 프로젝트를 읽게 하는 것이어야 합니다.

Codex는 다음 내용을 빠르게 파악하도록 도와줍니다.

  • 프로젝트가 어떤 기술 스택을 사용하는지.
  • 엔트리 파일이 어디에 있는지.
  • 핵심 모듈이 어디에 있는지.
  • 테스트와 빌드 명령이 무엇인지.
  • 어떤 파일을 함부로 건드리면 안 되는지.

많은 Codex 작업이 실패하는 이유는 코드를 못 써서가 아니라, 프로젝트를 이해하기 전에 바로 손대라고 요구받기 때문입니다.

코드 설명과 로직 정리

Codex는 이해하기 어려운 코드를 설명하는 데 도움을 줍니다.

예를 들면 다음과 같습니다.

  • 이 함수가 무엇을 하는지.
  • 이 컴포넌트를 왜 이렇게 작성했는지.
  • API 호출 흐름이 어떻게 되는지.
  • 상태가 어디에서 오는지.
  • 이 bug가 어떤 파일과 관련될 수 있는지.

Codex는 단일 함수만 설명하지 않습니다. 컨텍스트를 함께 보면서 모듈 관계, 데이터 흐름, 잠재적 위험도 정리합니다.

오래된 프로젝트를 인수할 때 특히 유용합니다.

bug 수정과 기능 추가

Codex는 경계가 분명한 개발 작업에 잘 맞습니다.

예를 들면 다음과 같습니다.

  • 재현 가능한 bug 수정.
  • 설정 페이지 추가.
  • 폼 검증 추가.
  • API 추가.
  • 내보내기 버튼 추가.
  • 프런트엔드 페이지 최적화.

하지만 큰 프로젝트 전체를 바로 던져 주어서는 안 됩니다.

더 좋은 방법은 작업을 작게 나누는 것입니다.

  1. 먼저 프로젝트를 읽습니다.
  2. 그다음 방안을 제시합니다.
  3. 모듈 하나만 수정합니다.
  4. 테스트를 실행합니다.
  5. diff를 확인합니다.
  6. 문제가 없음을 확인한 뒤 계속 진행합니다.

Codex는 큰 프로젝트를 한 번에 처리하기보다 작은 작업을 연속해서 완료하는 데 더 적합합니다.

테스트 작성과 리팩터링

Codex는 테스트 보완과 코드 리팩터링을 도와줍니다.

할 수 있는 일은 다음과 같습니다.

  • 단위 테스트 추가.
  • 경계 조건 추가.
  • 예외 시나리오 추가.
  • 중복 로직 추출.
  • 너무 긴 함수 분리.
  • 컴포넌트 구조 정리.
  • API 요청 래핑.

하지만 이런 작업에는 반드시 경계를 두어야 합니다.

  • 비즈니스 로직을 바꾸지 않습니다.
  • 공개 API를 바꾸지 않습니다.
  • 무관한 의존성을 도입하지 않습니다.
  • 대규모 리팩터링을 하지 않습니다.
  • 수정 후 반드시 테스트를 실행합니다.

Codex는 리팩터링할 수 있지만, 범위는 사용자가 통제해야 합니다.

문서 작성과 PR 정리

Codex는 엔지니어링 문서 작성에 잘 맞습니다.

예를 들면 다음과 같습니다.

  • README.
  • 설치 설명.
  • 시작 설명.
  • API 문서.
  • 환경 변수 설명.
  • 프로젝트 구조 설명.
  • PR 설명.
  • commit message.
  • 변경 로그.

문서는 부속물이 아닙니다.

Codex 워크플로에서 문서 자체가 컨텍스트 인프라입니다.

문서가 명확할수록 이후 사람과 AI가 프로젝트를 이어받기가 더 쉬워집니다.

하지만 Codex에게 다음을 알려 주어야 합니다.

존재하지 않는 명령을 지어내지 말고, 확실하지 않은 정보는 명확히 표시해야 합니다.

명령 실행, diff 확인, review

Codex와 일반 채팅 도구의 가장 큰 차이 중 하나는 프로젝트 환경에서 명령을 실행할 수 있다는 점입니다.

Codex는 다음을 할 수 있습니다.

  • 테스트 실행.
  • lint 실행.
  • typecheck 실행.
  • build 실행.
  • git status 확인.
  • git diff 확인.
  • 코드 검색.
  • 수정 결과 확인.

이 때문에 Codex는 단지 “답을 추측하는” 것이 아니라 결과를 검증할 수 있습니다.

하지만 명령 실행에는 위험도 있습니다.

검증할 수 있는 것은 검증하게 해도 됩니다.

위험한 것은 반드시 사용자가 승인해야 합니다.

프로덕션 환경, 데이터베이스, 실제 사용자 데이터와 관련된 작업은 자동으로 실행하게 맡기지 마십시오.

언제 Codex를 쓰기 좋은가

Codex에 적합한 작업에는 일반적으로 몇 가지 특징이 있습니다.

  • 목표가 명확합니다.
  • 범위를 통제할 수 있습니다.
  • 컨텍스트가 분명합니다.
  • 결과를 검증할 수 있습니다.
  • 실패해도 롤백할 수 있습니다.
  • 위험을 받아들일 수 있습니다.

예를 들면 다음과 같습니다.

  • 프로젝트 읽기.
  • bug 수정.
  • 작은 기능 추가.
  • 테스트 보완.
  • 문서 작성.
  • 프런트엔드 페이지 최적화.
  • PR 정리.
  • diff 검토.
  • 반복 작업 처리.
언제 Codex를 바로 쓰면 안 되는가

Codex에게 다음을 직접 처리하게 하는 것은 권장하지 않습니다.

  • 프로덕션 데이터베이스.
  • 실제 사용자 데이터.
  • 결제 핵심 로직.
  • 권한과 보안 핵심 모듈.
  • 대규모 아키텍처 마이그레이션.
  • 백업이 없는 중요한 프로젝트.
  • 테스트가 없는 핵심 비즈니스.
  • 사용자 자신도 검수할 수 없는 작업.

결과가 맞는지 판단할 수 없다면 Codex가 독립적으로 완료하게 하지 마십시오.

Codex는 효율을 높일 수 있지만, 사용자를 대신해 판단할 수는 없습니다.

한 문장 요약

Codex가 할 수 있는 일은 코드 작성에 그치지 않습니다.

정말 중요한 능력은 다음과 같습니다.

명확한 소프트웨어 엔지니어링 작업을 요구사항에서 review 가능한 결과까지 진행하는 것.

사용자는 Codex에게 아무 코드나 쓰라고 하는 것이 아닙니다.

프로젝트 규칙, 컨텍스트, 인수 기준에 따라 통제 가능한 엔지니어링 작업을 완료하게 하는 것입니다.

Codex와 ChatGPT의 차이

많은 사람이 묻습니다.

ChatGPT도 코드를 쓸 수 있는데 왜 Codex를 써야 할까요?

핵심 차이는 다음과 같습니다.

ChatGPT는 컨설턴트에 더 가깝습니다. 문제가 있으면 GPT에게 묻고, 답을 얻은 뒤 직접 실행합니다. 반면 지금의 Codex는 인턴에 더 가깝습니다. 실제로 일을 도와달라고 맡기고, 작업을 지시해 완료하게 할 수 있습니다.

ChatGPT는 문제를 생각하는 데 도움을 주기에 적합합니다.

Codex는 작업을 앞으로 진행하는 데 도움을 주기에 적합합니다.

더 합리적인 사용법은 다음과 같습니다.

먼저 ChatGPT로 생각을 정리하고, 그다음 Codex로 프로젝트에 들어가 실행합니다.

Codex와 Cursor의 차이

많은 사람이 Codex와 Cursor를 함께 비교합니다. 둘 다 코드 작성, 코드 수정, 프로젝트 이해를 도와줄 수 있기 때문입니다.

하지만 두 도구의 포지셔닝은 같지 않습니다.

Cursor는 AI 에디터에 더 가깝고, Codex는 엔지니어링 Agent에 더 가깝습니다.

합리적인 사용법은 조합해서 사용하는 것입니다.

일상적인 코딩과 국소적인 수정에는 Cursor를 쓰고, 작업 진행과 엔지니어링 전달에는 Codex를 사용합니다.

Cursor는 함께 작성하는 역할을 담당합니다.

Codex는 완전한 작업을 실행하도록 돕는 역할을 담당합니다.

하나는 IDE 협업에 가깝고, 다른 하나는 Agent 실행에 가깝습니다.

이것이 두 도구의 가장 큰 차이입니다.

Codex와 Claude Code의 차이

Codex와 Claude Code는 매우 비슷합니다.

둘 다 agentic coding 도구이며, 초점은 서로 다릅니다.

Claude Code는 터미널 안의 장기 협업에 더 가깝습니다

Claude Code의 경험은 다음과 더 비슷합니다.

터미널을 열고 프로젝트 안에 넣은 뒤, 개발 작업을 중심으로 계속 협업합니다.

다음에 적합합니다.

  • 오랫동안 프로젝트 읽기.
  • 복잡한 작업을 지속적으로 추적하기.
  • 터미널 안에서 논의하며 수정하기.
  • 여러 단계의 엔지니어링 문제 처리하기.
  • hooks, subagents, MCP 등의 메커니즘으로 워크플로 확장하기.

따라서 Claude Code는 터미널에 장기적으로 머무는 AI 엔지니어링 파트너에 더 가깝습니다.

장점은 명령줄 워크플로, 깊은 컨텍스트 협업, 엔지니어링 작업의 지속적 진행에 있습니다.

Codex는 OpenAI 생태계 안의 멀티 엔드 작업 실행에 더 가깝습니다

Codex의 장점은 CLI에만 있는 것이 아니라 OpenAI 생태계 안의 멀티 엔드 연동에 있습니다.

다양한 진입점으로 사용할 수 있습니다.

Codex CLI.

Codex App.

Codex IDE Extension.

Codex Web.

ChatGPT 계정 체계.

GitHub / PR 워크플로.

Skills와 프로젝트 규칙.

OpenAI 공식 문서에서 Codex CLI는 로컬 터미널 안의 coding agent입니다. Codex App은 데스크톱 멀티스레드, worktree, 자동화, Git 기능을 제공합니다. Codex Skills도 CLI, IDE extension, Codex app에서 재사용할 수 있습니다.

따라서 Codex는 OpenAI 생태계에 연결된 엔지니어링 작업 플랫폼에 더 가깝습니다.

단순히 “터미널에서 코드를 쓰는” 도구가 아닙니다. App, CLI, IDE, Web 같은 여러 진입점 사이를 오가며, 다양한 방식으로 엔지니어링 작업을 관리하고 실행하고 검토하게 해 줍니다.

어떻게 선택할까

터미널 워크플로를 더 선호하고, AI가 프로젝트 안에 오래 머물며 복잡한 작업을 중심으로 계속 협업하길 원한다면 Claude Code가 잘 맞습니다.

이미 ChatGPT와 OpenAI 생태계를 사용하고 있고, CLI, 데스크톱 App, IDE, Web 사이를 전환하면서 작업, diff, PR, Skills, GitHub 워크플로를 연결하고 싶다면 Codex가 더 편하게 느껴질 것입니다.

하지만 둘 중 하나가 절대적으로 다른 하나를 대체하는 것은 아닙니다.

최종 선택은 다음을 봐야 합니다.

  • 모델 능력.
  • 컨텍스트 처리.
  • 도구 체인.
  • 가격.
  • 팀 습관.
  • 자신의 개발 프로세스.

한 문장으로 정리하면 다음과 같습니다.

Claude Code는 터미널 안의 장기 엔지니어링 파트너에 더 가깝고, Codex는 OpenAI 생태계 안의 멀티 엔드 엔지니어링 Agent에 더 가깝습니다.

Codex 한 문장 요약

  • 초급 사용법: 코드 작성을 도와달라고 합니다.
  • 중급 사용법: 프로젝트 읽기, 기능 수정, 테스트 실행을 도와달라고 합니다.
  • 고급 사용법: 규칙, 컨텍스트, 자동화, 팀 프로세스와 함께 일하는 프로젝트 실행 대리인으로 만듭니다.

Codex의 사용 진입점

주로 로컬 프로젝트, 웹 연습, 일상 개발을 한다면 먼저 Codex App부터 시작하는 것만으로도 보통 충분합니다. Git, 터미널, 팀 협업에 익숙해진 뒤 CLI, IDE Extension, Web / Cloud를 점차 보완하면 됩니다.
