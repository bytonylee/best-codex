4부: 표준 워크플로

요구사항부터 전달까지 전 과정

많은 사람이 Codex를 처음 쓸 때 한 문장만 입력합니다:

웹사이트를 하나 만들어줘. 이 기능을 고쳐줘. 이 프로젝트를 최적화해줘.

이렇게 해도 동작할 수는 있지만, 한 가지 문제가 자주 생깁니다: AI는 빠르게 수정하지만, 무엇을 어떻게 바꿨는지, 안심하고 전달해도 되는지 알기 어렵습니다.

더 안정적인 방법은 Codex가 한 번에 마구 수정하게 두지 않고, 정해진 워크플로에 따라 진행하는 것입니다.

이렇게 이해하면 됩니다:

요구사항은 바로 결과물이 되지 않습니다. 그 사이에는 반드시 “이해, 계획, 수정, 검증, 점검, 인수” 단계를 거쳐야 합니다.

표준 6단계 방법

단계 이름 간단히 말하면 목적
1 요구사항 분해 먼저 Codex가 어떤 프로젝트를 다루는지 이해하게 합니다 구조를 모른 채 마구 수정하는 일을 피합니다
2 계획 수립 할 일을 먼저 나열하고 확인한 뒤 시작합니다 한 번에 너무 많이 수정하거나 방향이 어긋나는 일을 막습니다
3 작은 단위로 구현 한 번에 작은 부분 하나만 수정합니다 오류 가능성을 낮추고 롤백하기 쉽게 합니다
4 테스트 수정 후 검사를 실행하고 수동으로 검증합니다 코드에 뚜렷한 오류가 없는지 확인합니다
5 코드 리뷰 diff를 보고 수정이 맞는지, 위험은 없는지 확인합니다 AI가 수정하면 안 되는 곳을 건드리지 않게 합니다
6 커밋과 회고 코드를 커밋하고 배운 점을 기록합니다 AI는 실행을 맡고, 사람은 최종 판단을 합니다
1단계: 요구사항 분해

Codex에게 프로젝트 수정을 맡기기 전에는 코드 작성보다 요구사항 분해를 먼저 해야 합니다.

많은 사람이 Codex를 쓰다가 실패하는 이유는 Codex가 코드를 못 써서가 아니라, 처음 요구사항이 명확하지 않았기 때문입니다.

예를 들어 이렇게만 말하면:

홈페이지를 최적화해줘.

Codex는 이렇게 이해할 수 있습니다:

  • UI 수정
  • 문구 수정
  • 레이아웃 수정
  • 컴포넌트 구조 수정
  • 라우팅 수정
  • 심지어 자신이 “쓸모없다”고 판단한 코드까지 덤으로 삭제

본격적으로 시작하기 전에 요구사항을 몇 가지 핵심 질문으로 나눕니다.

배경은 무엇인가

먼저 이 작업을 왜 해야 하는지 설명합니다.

질문 예시
현재 프로젝트는 어떤 단계인가 이미 배포된 공식 웹사이트 페이지입니다
현재 어떤 상황을 겪고 있는가 홈페이지 전환율이 낮고, 사용자가 제품의 판매 포인트를 알기 어렵습니다
왜 지금 수정해야 하는가 새 버전 출시를 준비 중이라 첫 화면 표현을 최적화해야 합니다
이 요구사항은 어떤 유형인가 UI 최적화 / Bug 수정 / 새 기능 / 리팩터링
무엇을 해결해야 하는가

요구사항은 최대한 구체적으로 씁니다. “최적화”, “예쁘게”, “좀 더 좋게”처럼만 쓰면 부족합니다.

모호한 표현 더 명확한 표현
홈페이지 최적화 홈페이지 첫 화면의 제목, 부제목, CTA 버튼 최적화
페이지가 예쁘지 않음 카드 간격, 글꼴 위계, 버튼 스타일 조정
로그인에 문제가 있음 로그인 버튼 클릭 후 이동하지 않는 문제 수정
관리자 대시보드 만들기 검색, 필터, 페이지네이션이 포함된 사용자 목록 페이지 추가

좋은 요구사항은 다음 질문에 답할 수 있어야 합니다:

이번에 정확히 어떤 구체적인 문제를 해결하려는가?

예시:

이번에는 주로 세 가지 문제를 해결합니다:
1. 첫 화면 제목이 명확하게 전달되지 않음
2. CTA 버튼이 눈에 잘 띄지 않음
3. 모바일 첫 화면 콘텐츠가 너무 빽빽함
어떤 파일이 관련될 수 있는가

대략적인 파일 위치를 알고 있다면 Codex에게 미리 알려주는 편이 좋습니다.

이렇게 하면 Codex가 프로젝트 전체를 마구 찾고 수정할 가능성이 줄어듭니다.

상황 관련될 수 있는 파일
홈페이지 수정 app/page.tsx, pages/index.tsx, components/Hero.tsx
스타일 수정 globals.css, tailwind.config.js, 관련 컴포넌트 파일
로그인 수정 login/page.tsx, auth.ts, middleware.ts
API 수정 api 디렉터리, server 디렉터리, lib 디렉터리
문구 수정 페이지 컴포넌트, 설정 파일, i18n 파일
어떤 기능을 건드리면 안 되는가

이 점은 중요합니다.

Codex는 현재 작업을 끝내려다가 다른 곳까지 바꾸기 쉽습니다.

그래서 미리 알려줘야 합니다:

건드리면 안 되는 내용 설명
로그인 로직 UI만 수정하고 인증 흐름은 수정하지 않습니다
API 주소 API 요청 경로를 바꾸지 않습니다
데이터 구조 데이터베이스 필드를 바꾸지 않습니다
라우팅 구조 기존 페이지 경로를 바꾸지 않습니다
기존 컴포넌트 필요하지 않으면 큰 리팩터링을 하지 않습니다
의존성 버전 의존성을 임의로 업그레이드하거나 추가하지 않습니다

이 단계에서는 Codex에게 경계를 그어 줍니다.

어떤 결과를 완료로 볼 것인가

“다 하면 됨”이라고만 말하지 말고 Codex에게 완료 기준을 알려줘야 합니다.

요구사항 유형 완료 기준
UI 최적화 페이지 시각 품질이 뚜렷하게 개선되고 모바일에서도 깨지지 않음
Bug 수정 기존 오류가 사라지고 관련 기능을 정상적으로 사용할 수 있음
새 기능 사용자가 전체 작업 흐름을 끝까지 수행할 수 있음
성능 최적화 빌드가 정상이고 페이지 로딩이 눈에 띄게 느려지지 않음
문구 최적화 제목, 부제목, 버튼 문구가 더 명확함

예시:

완료 기준:
1. 홈페이지 첫 화면이 제품 용도를 명확하게 표현함
2. CTA 버튼이 더 눈에 잘 띔
3. 모바일 표시가 정상임
4. 다른 페이지에 영향을 주지 않음
5. 프로젝트를 정상적으로 실행하고 빌드할 수 있음
어떤 테스트가 필요한가

수정 후에는 Codex가 “완료했다”고 말하는 것만 보지 말고, 검증 방법도 미리 정해야 합니다.

테스트 유형 적용 상황
페이지 미리보기 UI 수정, 페이지 레이아웃 조정
콘솔 확인 프런트엔드 페이지, 인터랙션 기능
빌드 테스트 Next.js, React, Vue 프로젝트
단위 테스트 테스트 파일이 있는 프로젝트
수동 흐름 테스트 로그인, 결제, 폼, 업로드 등 흐름
모바일 테스트 반응형 페이지, 샤오홍슈 첫 이미지, 모바일 웹페이지
어떤 위험이 있는가

요구사항을 분해할 때 Codex가 위험도 미리 판단하게 합니다.

그러면 수정 중에 이것저것 마구 시도하지 않게 됩니다.

위험 설명
영향 범위가 너무 큼 작은 요구사항이 큰 리팩터링으로 변함
스타일 오염 전역 CSS를 수정해 다른 페이지에 영향을 줌
의존성 위험 불필요한 의존성을 추가해 프로젝트가 복잡해짐
로직 위험 한 문제를 고치려다 다른 흐름을 망가뜨림
데이터 위험 API, 필드, 데이터베이스 관련 내용을 수정함
호환성 위험 데스크톱에서는 정상인데 모바일에서 문제가 생김
요구사항 분해 프롬프트 템플릿

Codex에서 실제로 사용할 때는 이 내용을 바로 복사해도 됩니다:

먼저 요구사항 분해를 도와주세요. 바로 코드를 수정하지 마세요.

요구사항:
[여기에 요구사항을 작성하세요]

아래 구조에 따라 분석해 주세요:

1. 배경은 무엇인가
- 현재 프로젝트는 대략 무엇인가
- 왜 이 요구사항을 해야 하는가
- 이 요구사항은 새 기능, Bug 수정, UI 최적화, 리팩터링 중 무엇인가

2. 무엇을 해결해야 하는가
- 현재 구체적인 문제는 무엇인가
- 이번에 어느 정도까지 해결해야 하는가
- 이번 범위에 포함되지 않는 내용은 무엇인가

3. 어떤 파일이 관련될 수 있는가
- 프로젝트 구조를 바탕으로 관련될 수 있는 파일을 판단해 주세요
- 먼저 목록만 작성하고, 바로 수정하지 마세요

4. 어떤 기능을 건드리면 안 되는가
- 어떤 로직을 바꾸면 안 되는가
- 어떤 API를 건드리면 안 되는가
- 어떤 페이지나 컴포넌트에 영향을 주면 안 되는가

5. 어떤 결과를 완료로 볼 것인가
- 기능 완료 기준
- 페이지 완료 기준
- 코드 완료 기준

6. 어떤 테스트가 필요한가
- 어떤 명령을 실행해야 하는가
- 어떤 페이지를 수동으로 확인해야 하는가
- 어떤 흐름을 중점적으로 검증해야 하는가

7. 어떤 위험이 있는가
- 어떤 기능에 영향을 줄 수 있는가
- 스타일 오염 위험이 있는가
- 과도한 리팩터링 위험이 있는가
- 새 의존성 추가 위험이 있는가

마지막으로 짧은 실행 제안을 주세요:
- 먼저 어떤 단계부터 하는 것이 좋은가
- 제가 확인한 뒤 수정해야 하는가
2단계: Codex가 계획을 세우게 하기

요구사항 분해가 끝났다고 바로 Codex에게 코드를 쓰게 하면 안 됩니다.

이 단계에서는 Codex가 먼저 계획을 세우게 합니다.

이렇게 이해하면 됩니다:

먼저 AI가 어떻게 작업할지 설명하게 한 뒤, 실행 여부를 결정합니다.

많은 프로젝트가 실패하는 이유는 Codex가 수정할 수 없어서가 아니라, 처음부터 바로 수정하기 때문입니다.

방향이 틀렸다는 것을 발견했을 때는 이미 많은 파일이 바뀌어 있을 수 있습니다. 다시 확인하고 롤백하기도 번거롭습니다.

2단계의 핵심은 다음과 같습니다:

먼저 계획하고, 나중에 실행합니다. 먼저 확인하고, 나중에 수정합니다.

먼저 코드를 작성하지 않기

이 문장은 프롬프트 맨 앞에 써야 합니다.

Codex는 요구사항을 보면 바로 문제를 해결하려는 경향이 있습니다.

실제 프로젝트에서 바로 코드를 수정하는 것은 위험합니다.

바로 코드를 작성할 때의 문제 가능한 결과
프로젝트 구조를 이해하지 못함 잘못된 파일을 수정함
요구사항 경계를 확인하지 않음 범위 밖 기능까지 만듦
영향 범위를 판단하지 않음 기존 기능을 잘못 건드림
테스트 방식을 나열하지 않음 수정 후 어떻게 검증할지 모름
한 번에 너무 많이 수정함 오류가 난 뒤 롤백하기 어려움

예시 프롬프트:

먼저 코드를 작성하지 말고, 어떤 파일도 수정하지 마세요.
현재 요구사항과 프로젝트 구조를 바탕으로 먼저 수정 계획을 세워 주세요.
제가 확인한 뒤 실행을 시작하세요.
계획 모드 켜기

앞에서 설명한 Codex App 기본 사용법의 "계획 모드" 절을 참고할 수 있습니다. 실제로 사용할 때는 Codex CLI 또는 App에 /plan을 바로 입력해 Codex가 먼저 계획을 출력하게 한 뒤, 실행할지 결정해도 됩니다.

3단계: 작은 단위로 구현

계획을 확인한 뒤에 실제 코드 수정 단계로 들어갑니다.

여기에는 중요한 원칙이 하나 있습니다:

Codex가 모든 것을 한 번에 수정하게 하지 마세요.

많은 사람이 Codex를 쓰다가 실패하는 이유는 시작하자마자 “전부 구현”하게 하기 때문입니다.

그 결과 Codex가 페이지, 컴포넌트, 스타일, API, 설정을 동시에 바꿀 수 있습니다. 프로젝트가 겉으로는 바뀐 것처럼 보여도 어디에서 문제가 생겼는지 판단하기 어렵습니다.

더 안정적인 방법은 다음과 같습니다:

한 번에 기능 포인트 하나만 수정합니다. 작은 단계 하나를 수정한 뒤, 그 단계 하나를 확인합니다.

한 번에 기능 포인트 하나만 수정하기

작은 단위 구현에서는 수정 범위를 통제해야 합니다.

예를 들어 홈페이지를 최적화할 때는 이렇게 한 번에 말하지 마세요:

전체 홈페이지를 최적화해 주세요.

대신 이렇게 나눕니다:

단계 수정 내용
1단계 첫 화면 제목과 부제목만 최적화
2단계 CTA 버튼만 조정
3단계 모바일 레이아웃만 최적화
4단계 제품 판매 포인트 카드만 보충
5단계 최종 스타일 세부 사항만 처리

이렇게 하면 각 단계가 명확해지고, 문제가 생겨도 위치를 찾기 쉽습니다.

Codex가 관련 없는 코드를 리팩터링하지 않게 하기

Codex는 때때로 어떤 코드가 “충분히 깔끔하지 않다”고 판단하고 함께 리팩터링하려 합니다.

실제 프로젝트에서 부수적인 리팩터링은 위험합니다.

Codex가 시도할 수 있는 작업 생길 수 있는 문제
컴포넌트 이름 변경 참조 경로 오류를 일으킴

4단계: 테스트

Codex가 작은 단위 수정을 완료한 뒤 바로 다음 단계로 넘어가면 안 됩니다. 반드시 먼저 테스트해야 합니다.

Codex를 사용할 때 많은 사람이 겪는 가장 큰 문제는 다음과 같습니다:

AI는 완료했다고 말했지만 실제로는 프로젝트가 실행되지 않습니다. 페이지는 정상처럼 보이지만 일부 기능은 이미 망가졌습니다. 현재 기능은 고쳐졌지만 기존 기능이 영향을 받았습니다.

테스트의 핵심은 Codex가 “완료”라고 말한 것을 믿는 것이 아니라, 결과로 실제 완료를 증명하는 것입니다.

아래 표는 전체 테스트에서 해야 할 일을 빠른 것부터 느린 것 순서로 정리한 것입니다:

테스트 유형 역할 일반적인 명령 중점
단위 테스트 함수, 컴포넌트, 모듈이 정상 동작하는지 확인 npm test / pnpm test / yarn test 실패하면 먼저 원인을 설명하고, 바로 코드를 수정하지 않습니다
타입 검사 TypeScript 프로젝트에서 타입 오류를 미리 발견 npm run typecheck / tsc --noEmit 해당 명령이 없으면 명확히 설명합니다
lint 코드 규칙 문제(사용하지 않는 변수, import 순서, Hook 사용법 등)를 확인 npm run lint 이번에 새로 생긴 문제와 프로젝트 기존 문제를 구분합니다
빌드 로컬에서 열린다고 배포 가능한 것은 아니며, 빌드가 되어야 패키징할 수 있습니다 npm run build / pnpm build 실패하면 먼저 오류와 영향 범위를 요약합니다
수동 테스트 UI, 폼, 로그인, 결제, 업로드는 직접 눌러봐야 합니다 없음 사용자 작업 경로에 따라 단계별로 검증합니다
브라우저 테스트 터미널만으로는 보이지 않는 페이지/콘솔/API 문제 없음 페이지 표시, Console 오류, Network, 모바일 레이아웃을 확인합니다
회귀 테스트 새 기능뿐 아니라 기존 기능이 망가지지 않았는지도 테스트합니다 없음 이번 수정이 영향을 줄 수 있는 기존 페이지와 컴포넌트를 나열합니다

두 가지를 기억하세요. 많은 오래된 프로젝트에는 원래부터 lint나 타입 문제가 있습니다. Codex가 기존 문제까지 함께 리팩터링하게 하지 마세요. 회귀 테스트는 초보자가 가장 쉽게 놓치는 단계입니다. 홈페이지 버튼만 바꿔도 같은 컴포넌트를 재사용하는 다른 페이지에 영향을 줄 수 있습니다.

수동 테스트 시에는 Codex에게 검증 단계를 "작업과 예상 결과" 표로 정리하게 할 수 있습니다. 예를 들면:

단계 작업 예상 결과
1 홈페이지 열기 페이지가 정상적으로 로드됨
2 CTA 버튼 클릭 가입 페이지로 이동함
3 휴대폰 너비로 줄이기 페이지가 깨지지 않음
4 콘솔 열기 콘솔에 뚜렷한 빨간 오류가 없음
테스트 단계 프롬프트 템플릿

실제로 사용할 때는 이 내용을 바로 복사해도 됩니다:

이번 수정에 대해 테스트를 진행해 주세요. 새 기능을 계속 추가하지 마세요.

아래 순서대로 실행하거나 설명해 주세요:

1. 단위 테스트
- 프로젝트에 단위 테스트가 있는지
- 있다면 테스트 명령을 실행해 주세요
- 실패하면 실패 원인을 설명해 주세요

2. 타입 검사
- 프로젝트에 typecheck 명령이 있는지
- 있다면 실행해 주세요
- 없다면 설명해 주세요

3. lint
- lint 검사를 실행해 주세요
- 이번에 새로 생긴 문제와 프로젝트 기존 문제를 구분해 주세요

4. 빌드
- build 명령을 실행해 주세요
- 실패하면 오류 원인과 영향 범위를 설명해 주세요

5. 수동 테스트
- 수동 테스트가 필요한 페이지를 나열해 주세요
- 사용자 작업 단계를 나열해 주세요
- 각 단계의 예상 결과를 나열해 주세요

6. 브라우저 테스트
- 페이지 표시 확인
- 콘솔 오류 확인
- 모바일 레이아웃 확인
- 핵심 버튼과 인터랙션 확인

7. 회귀 테스트
- 이번 수정이 기존 기능에 영향을 주는지 확인

마지막으로 테스트 요약을 출력해 주세요:
- 어떤 테스트가 통과했는지
- 어떤 테스트가 실패했는지
- 실패 원인은 무엇인지
- 다음 단계로 넘어갈 수 있는지
- 문제를 먼저 수정해야 하는지
5단계: 코드 리뷰

테스트를 통과했다고 이번 수정을 바로 전달할 수 있는 것은 아닙니다.

코드 리뷰도 필요합니다.

코드 리뷰에서는 다음을 확인합니다:

코드가 실행되는지만 보지 말고, 수정이 맞는지와 안정적인지, 위험은 없는지도 봅니다.

Codex는 코드를 빠르게 작성하지만, 다음과 같은 문제가 생길 수 있습니다:

일반적인 문제 설명
기능은 실행되지만 로직이 맞지 않음 겉보기에는 정상이나 실제 비즈니스 흐름에 문제가 있음
수정 범위가 너무 큼 작은 요구사항 하나 때문에 관련 없는 코드를 많이 수정함
기존 로직을 잘못 삭제함 쓸모없어 보이지만 실제로는 필요한 코드를 삭제함
경계 조건을 무시함 정상 입력은 동작하지만 비정상 입력에서는 깨짐
보안 문제 키 노출, 권한 판단 오류, 입력 검증 누락
스타일이 통일되지 않음 새 코드가 기존 프로젝트 작성 방식과 일치하지 않음
유지보수성이 낮음 임시 하드코딩 때문에 이후 수정이 어려움

코드 리뷰는 선택 사항이 아니라 Codex 워크플로의 핵심 단계입니다.

두 차례 리뷰: Codex 자체 리뷰 + 사람 리뷰

첫 번째는 Codex가 방금 한 수정을 스스로 점검하게 합니다. 목적은 완전히 믿는 것이 아니라 명백한 문제를 먼저 드러내게 하는 것입니다. 표로 출력하게 하는 편이 좋습니다:

검사 항목 결과 설명
계획 밖 파일을 수정했는가 아니요 홈페이지 관련 컴포넌트만 수정했습니다
의존성을 새로 추가했는가 아니요 package.json을 수정하지 않았습니다
기존 로직을 삭제했는가 아니요 기존 버튼 이동 로직을 유지했습니다
위험이 있는가 있음 모바일 버튼 간격은 아직 사람이 확인해야 합니다

두 번째는 사람 리뷰입니다. 최종 전달자는 Codex가 아니라 당신입니다. 모든 줄을 다 이해할 필요는 없지만, diff에서 다음 부분은 중점적으로 봅니다:

리뷰 중점 무엇을 볼 것인가
파일 범위 수정해야 할 파일만 수정했는지
수정 / 삭제 내용 계획에 맞는지, 기존 기능을 삭제하지 않았는지
이름과 구조 기존 프로젝트 스타일과 일치하는지
비즈니스 로직 실제 요구사항에 맞는지(실행됨 ≠ 로직이 맞음)
테스트 결과 정말 테스트를 실행했는지

로그인, 결제, 권한, 데이터베이스, 인증 등 중요한 코드가 관련되어 있다면 두 번째 모델로 교차 리뷰를 해도 좋습니다. 한 모델이 작성하고, 다른 모델은 문제만 찾게 하는 방식입니다. 문구 수정이나 가벼운 스타일 수정에는 보통 필요하지 않습니다. 두 번째 모델의 제안도 그대로 모두 받아들이면 안 됩니다. 문제 발견을 도와줄 뿐, 최종 결정을 대신하지 않습니다.

네 가지 고위험 문제를 중점적으로 보기

Codex는 아래 네 가지 영역에서 문제를 일으키기 쉬우므로 중점적으로 리뷰해야 합니다:

분류 일반적인 문제 리뷰 포인트
경계 조건 정상 입력은 동작하지만 비정상 입력에서는 깨짐 빈 데이터, API 실패, 미로그인, 권한 부족, 모바일 크기, 반복 클릭
보안 문제 사용자/API/권한/결제/업로드/데이터베이스와 관련될 때 키나 token을 노출하는지, 권한 판단이 빠졌는지, 입력 검증이 있는지, 민감한 정보를 유출하는지, API 인증이 있는지
잘못 삭제했는지 쓸모없어 보이지만 실제로 필요한 코드가 삭제됨 diff의 삭제 내용을 중점적으로 봅니다. 기존 컴포넌트, 주석, 호환 코드, fallback, 설정 항목은 여전히 사용 중일 수 있습니다
비즈니스 로직 코드는 실행되지만 로직이 틀림(잘못된 페이지 이동, 가격 계산 오류, 권한 초과) 정상 경로, 예외 경로, 권한 판단, 기존 비즈니스 규칙을 덮어썼는지

Codex가 명확히 설명하지 않은 대량 삭제는 바로 받아들이지 마세요.

코드 리뷰 프롬프트 템플릿

실제로 사용할 때는 이 내용을 바로 복사해도 됩니다:

이번 수정에 대해 코드 리뷰를 해 주세요. 코드를 계속 작성하지 마세요.

아래 구조에 따라 리뷰해 주세요:

1. Codex 자체 리뷰
- 이번에 계획된 파일만 수정했는지
- 관련 없는 리팩터링이 있는지
- 새 의존성이 있는지
- 하드코딩이 있는지
- 기존 로직을 잘못 삭제했는지

2. 수정 범위 리뷰
- 어떤 파일을 수정했는지
- 각 파일을 왜 수정했는지
- 계획 밖 수정이 있는지
- 설명 없는 대규모 수정이 있는지

3. 경계 조건 리뷰
- 빈 데이터를 어떻게 처리하는지
- API 실패를 어떻게 처리하는지
- 사용자가 로그인하지 않은 경우 어떻게 처리하는지
- 권한 부족을 어떻게 처리하는지
- 반복 클릭을 어떻게 처리하는지
- 모바일에서 이상이 생길 수 있는지

4. 보안 문제 리뷰
- 키, token, 계정 비밀번호를 노출하는지
- 권한 판단에 영향을 주는지
- 입력 검증이 빠졌는지
- 민감한 정보가 유출될 수 있는지
- API 인증 로직을 수정했는지

5. 삭제 내용 리뷰
- 어떤 코드를 삭제했는지
- 삭제 이유는 무엇인지
- 다른 곳에서 의존하지 않는 것이 확인되었는지
- 기존 기능에 영향을 줄 수 있는지

6. 비즈니스 로직 리뷰
- 요구사항에 맞는지
- 정상 흐름이 올바른지
- 예외 흐름이 올바른지
- 기존 비즈니스 규칙에 영향을 주는지
- 불확실한 비즈니스 가정이 있는지

7. 리뷰 결론
마지막에 결론을 주세요:
- 계속 진행 가능
- 작은 수정 필요
- 일부 수정 롤백 필요
- 계획을 다시 세워야 함

주의:
리뷰만 하고 코드를 계속 수정하지 마세요.
문제를 발견하면 먼저 문제와 제안을 설명하고, 제가 확인한 뒤 수정하세요.
6단계: 커밋과 회고

코드가 테스트를 통과하고 리뷰까지 끝난 뒤에도 마지막 단계는 단순히 “완료했다”고 말하는 것이 아닙니다.

완전한 Codex 워크플로에는 두 가지가 더 필요합니다:

첫째, 이번 수정을 공식적으로 커밋합니다. 둘째, 이번 경험을 기록합니다.

많은 사람이 Codex를 “코드가 실행되는” 단계까지만 사용하고 커밋 설명, PR 설명, 문제 기록, 문서 업데이트는 남기지 않습니다.

단기적으로는 문제가 없어 보이지만, 장기적으로는 이런 번거로움이 생깁니다:

매번 처음 하는 것처럼 됩니다. 매번 다시 설명해야 합니다. 매번 같은 시행착오를 반복합니다.

그래서 6단계의 핵심은 다음과 같습니다:

전달이 끝이 아닙니다. 회고가 다음 수정의 효율을 높입니다.

commit 생성

이번 수정이 테스트와 리뷰를 통과했다면 Codex에게 commit 생성을 요청할 수 있습니다.

commit은 “update” 한마디로 대충 쓰지 말고, 이번에 정확히 무엇을 바꿨는지 설명해야 합니다.

좋은 commit은 다음 질문에 답할 수 있어야 합니다:

질문 설명
무엇을 바꿨는가 이번 커밋의 주요 내용
왜 바꿨는가 어떤 요구사항 또는 문제에 대응하는가
어디에 영향을 주는가 어떤 모듈, 페이지, 기능이 관련되는가
테스트를 통과했는가 빌드, lint, 테스트를 통과했는가

일반적인 commit message 형식:

feat: add user profile page
fix: resolve login redirect issue
style: improve homepage responsive layout
refactor: simplify product card component
docs: update setup guide

현지화 프로젝트라면 팀에서 사용하는 언어로 설명을 작성할 수도 있습니다:

feat: 사용자 프로필 페이지 추가
fix: 로그인 후 이동 이상 수정
style: 홈페이지 모바일 레이아웃 최적화
docs: 프로젝트 사용 설명 업데이트
PR 작성

프로젝트가 GitHub, GitLab 또는 팀 협업 흐름을 사용한다면 커밋 후 보통 PR도 작성합니다.

PR은 “형식적인 절차”가 아니라 다른 사람이 빠르게 이해하도록 돕는 문서입니다:

PR에서 설명해야 할 것 역할
이번에 무엇을 했는가 reviewer가 빠르게 이해할 수 있게 합니다
왜 해야 했는가 요구사항 배경을 설명합니다
어디를 바꿨는가 리뷰 비용을 낮춥니다
어떻게 테스트했는가 임의로 바꾼 것이 아님을 보여줍니다
어떤 위험이 있는가 불확실한 지점을 미리 드러냅니다
어디를 중점적으로 봐야 하는가 reviewer가 볼 중점을 안내합니다

좋은 PR 설명은 이렇게 쓸 수 있습니다:

## 이번 수정

- 홈페이지 첫 화면 제목, 부제목, CTA 버튼 최적화
- 모바일 첫 화면 레이아웃 조정
- 기존 이동 로직은 유지하고, API와 라우팅은 수정하지 않음

## 테스트 결과

- npm run lint 통과
- npm run build 통과
- 홈페이지 데스크톱과 모바일 표시를 수동 확인했고 정상
- CTA 버튼 클릭 이동 정상

## 위험 설명

- 이번에는 홈페이지 스타일 조정이 포함되어 있어 모바일 표시를 중점적으로 확인해야 함
- 새 의존성 없음
- 로그인, API, 데이터베이스 로직 수정 없음
문제 기록

회고할 때는 이번 과정에서 만난 문제를 기록합니다.

이 단계는 중요합니다.

Codex 워크플로에서 중요한 가치는 “이번에 끝냈다”가 아니라 다음에 있습니다:

다음에 비슷한 문제를 만나면 같은 시행착오를 줄일 수 있습니다.

기록해야 할 문제에는 다음이 포함됩니다:

문제 유형 예시
요구사항 문제 처음 요구사항 설명이 충분히 명확하지 않았음
계획 문제 Codex 계획에서 모바일을 빠뜨림
수정 문제 Codex가 관련 없는 컴포넌트를 덤으로 수정함
테스트 문제 프로젝트에 typecheck 명령이 없음
리뷰 문제 fallback 로직을 잘못 삭제한 것을 발견함
커뮤니케이션 문제 프롬프트에 “새 의존성 추가 금지”를 명확히 쓰지 않음

기록 형식은 아주 간단해도 됩니다:

이번 문제 기록:

1. 문제: Codex가 처음에 전역 스타일을 수정하려고 함
   원인: 요구사항에서 “홈페이지만 수정”이라고 명확히 제한하지 않음
   해결: 프롬프트를 보완해 홈페이지 관련 파일만 수정하도록 요구

2. 문제: 모바일 테스트 누락
   원인: 계획 단계에서 모바일 인수 기준을 나열하지 않음
   해결: 앞으로 테스트 체크리스트에 모바일 확인을 고정으로 추가

3. 문제: PR 설명이 충분히 명확하지 않음
   원인: 테스트 결과를 미리 기록하지 않음
   해결: 매번 테스트 후 바로 테스트 요약 생성
프롬프트 정리

이번에 사용한 프롬프트 효과가 좋았다면 그것도 기록합니다.

이 단계의 목적은 간단합니다:

잘 작동한 프롬프트는 매번 다시 쓰지 않습니다.

예를 들어 이번에 아래 문장이 유용하다는 것을 발견했다면:

관련 없는 코드를 덤으로 리팩터링하지 마세요.
계획을 넘어서는 수정이 필요하다는 것을 발견하면 먼저 멈춰서 저에게 질문해 주세요.

기록해 두고 앞으로 고정 규칙으로 사용합니다.

표로 정리할 수 있습니다:

효과적인 프롬프트 적용 상황 효과적인 이유
먼저 코드를 작성하지 말고, 먼저 계획을 세우세요 모든 복잡한 요구사항 Codex가 바로 마구 수정하는 것을 방지합니다
한 번에 기능 포인트 하나만 수정하세요 여러 단계 작업 오류와 롤백 비용을 낮춥니다
관련 없는 코드를 덤으로 리팩터링하지 마세요 오래된 프로젝트 유지보수 수정 범위가 커지는 것을 막습니다
수정 완료 후 diff를 요약하세요 매번 수정 후 사람 리뷰를 쉽게 합니다
불확실하면 먼저 멈추고 질문하세요 비즈니스 로직이 명확하지 않을 때 AI가 독단적으로 판단하는 것을 방지합니다
AGENTS.md 업데이트

앞으로 매번 지켜야 할 규칙이 있다면 채팅에만 쓰지 말고, 프로젝트 수준의 AGENTS.md에 업데이트하는 것이 좋습니다.

AGENTS.md는 이렇게 이해할 수 있습니다:

Codex에게 주는 프로젝트 규칙 설명서입니다.

이 파일은 Codex에게 다음을 알려줄 수 있습니다:

내용 역할
프로젝트 실행 방법 Codex에게 시작, 테스트, 빌드 명령을 알려줍니다
코드 스타일 프로젝트 스타일에 맞지 않는 코드를 만들지 않게 합니다
건드리면 안 되는 디렉터리 핵심 파일을 잘못 수정하는 일을 막습니다
수정 전에 해야 할 일 “먼저 계획하고 나중에 실행”을 규칙으로 고정합니다
테스트 요구사항 수정 후 어떤 검사를 반드시 실행할지 정합니다
제출 요구사항 commit과 PR 작성 방식을 정합니다

예시 내용:

# AGENTS.md

## 작업 규칙

- 수정 전 반드시 프로젝트 구조를 먼저 읽습니다.
- 수정 전 반드시 계획을 먼저 세우고, 바로 코드를 작성하지 않습니다.
- 한 번에 기능 포인트 하나만 구현합니다.
- 관련 없는 코드를 덤으로 리팩터링하지 않습니다.
- 불필요한 의존성을 추가하지 않습니다.
- 비즈니스 로직이 불확실하면 먼저 질문하고, 스스로 결정하지 않습니다.

## 테스트 요구사항

매번 수정 후 최소한 다음을 확인합니다:

- npm run lint
- npm run build
- 관련 페이지 수동 테스트
- 브라우저 콘솔에 오류가 있는지
- 모바일 레이아웃이 정상인지

## 제출 요구사항

제출 전에는 다음을 설명해야 합니다:

- 어떤 파일을 수정했는지
- 각 파일에서 무엇을 바꿨는지
- 테스트를 통과했는지
- 위험이나 미완료 사항이 있는지
프로젝트 문서 업데이트

AGENTS.md 외에도, 이번 수정이 프로젝트 사용 방식에 영향을 주었다면 프로젝트 문서도 업데이트해야 합니다.

예를 들면:

수정 내용 업데이트해야 할 문서
새 기능 README, 기능 설명
새 환경 변수 .env.example, 배포 문서
새 명령 README, 개발 가이드
API 수정 API 문서
배포 흐름 수정 배포 설명
설정 수정 설정 설명
새 컴포넌트 컴포넌트 사용 설명

문서 업데이트는 보기 좋으라고 하는 작업이 아니라, 나중에 잊어버리지 않기 위한 작업입니다.

일반적인 문서는 다음과 같습니다:

파일 역할
README.md 프로젝트 소개, 시작 방법, 자주 쓰는 명령
.env.example 환경 변수 예시
docs/ 상세 프로젝트 문서
CHANGELOG.md 버전 업데이트 기록
AGENTS.md Codex 작업 규칙
CONTRIBUTING.md 팀 협업 규칙
커밋과 회고 프롬프트 템플릿

실제로 사용할 때는 아래 내용을 바로 복사해도 됩니다:

커밋과 회고 단계로 들어가 주세요. 새 기능을 계속 추가하지 마세요.

아래 구조에 따라 출력해 주세요:

1. Commit 제안
- 적절한 commit message를 생성해 주세요
- conventional commit 형식을 사용해 주세요
- 이번 수정 범위를 과장하지 마세요

2. PR 설명
PR 내용을 생성해 주세요. 포함할 내용:
- 이번 수정
- 수정 이유
- 관련 파일
- 테스트 결과
- 위험 설명
- reviewer가 중점적으로 봐야 할 곳

3. 문제 기록
이번 과정을 회고해 주세요:
- 어떤 문제를 만났는지
- 원인은 무엇인지
- 어떻게 해결했는지
- 다음에는 어떻게 피할지

4. 프롬프트 정리
다음을 정리해 주세요:
- 어떤 프롬프트가 효과적이었는지
- 왜 효과적이었는지
- 어떤 상황에서 재사용하기 좋은지
- AGENTS.md에 추가하는 것을 권장하는지

5. AGENTS.md 업데이트 제안
AGENTS.md에 넣기 좋은 장기 규칙을 출력해 주세요:
- 수정 전 규칙
- 수정 중 규칙
- 테스트 규칙
- 제출 규칙

6. 프로젝트 문서 업데이트 제안
업데이트가 필요한지 판단해 주세요:
- README.md
- .env.example
- docs/
- CHANGELOG.md
- 기타 프로젝트 문서

마지막으로 전달 결론을 주세요:
- 커밋할 수 있는지
- PR을 보낼 수 있는지
- 아직 미완료 사항이 있는지
- 사람이 확인해야 할 위험이 있는지

Codex 작업 템플릿 모음

앞에서는 Codex의 표준 워크플로를 설명했습니다.

이 절에는 자주 쓰는 템플릿을 바로 복사해 쓸 수 있게 정리합니다.

이 템플릿의 역할은 다음과 같습니다:

매번 프롬프트를 새로 만들지 말고, 상황에 맞는 템플릿을 복사한 뒤 자신의 요구사항을 채웁니다.

프로젝트 읽기 템플릿

이 템플릿은 새 프로젝트를 처음 열었을 때 사용하기 좋습니다.

Codex가 어떤 프로젝트를 처음 접하는 경우, 시작하자마자 코드를 수정하게 하지 마세요.

더 안정적인 방식은 먼저 프로젝트를 읽게 한 뒤, 프로젝트 이해 보고서를 출력하게 하는 것입니다.

그러면 다음을 먼저 판단할 수 있습니다:

확인 지점 역할
Codex가 프로젝트를 이해했는지 처음부터 잘못된 파일을 수정하지 않게 합니다
기술 스택 판단이 올바른지 프로젝트가 어떤 프레임워크를 쓰는지 알고 있는지 확인합니다
시작 방법이 명확한지 이후 테스트와 실행이 더 순조로워집니다
핵심 모듈을 제대로 찾았는지 후속 수정에서 방향을 잃지 않게 합니다
위험이 미리 드러났는지 핵심 로직을 잘못 수정하는 일을 막습니다
프로젝트 읽기 템플릿(바로 복사 가능)
먼저 어떤 코드도 수정하지 마세요.

현재 프로젝트를 읽고 프로젝트 이해 보고서를 출력해 주세요. 포함할 내용:

1. 기술 스택
- 프로젝트가 사용하는 주요 기술
- 프런트엔드/백엔드/데이터베이스/빌드 도구가 각각 무엇인지
- TypeScript, Tailwind, 프레임워크 또는 컴포넌트 라이브러리를 사용하는지

2. 디렉터리 구조
- 주요 디렉터리가 각각 무엇을 담당하는지
- 페이지, 컴포넌트, 유틸리티 함수, API, 설정 파일이 각각 어디에 있는지
- 어떤 디렉터리가 핵심 디렉터리이고, 어떤 디렉터리는 함부로 수정하지 않는 것이 좋은지

3. 시작 방법
- 프로젝트 의존성을 어떻게 설치하는지
- 프로젝트를 로컬에서 어떻게 시작하는지
- 환경 변수가 필요한지
- README에 설명이 있다면 README를 우선 참고해 주세요

4. 테스트 명령
- 프로젝트에 test 명령이 있는지
- lint 명령이 있는지
- typecheck 명령이 있는지
- build 명령이 있는지
- 관련 명령이 없다면 명확히 설명해 주세요

5. 핵심 모듈
- 프로젝트의 핵심 기능 모듈은 무엇인지
- 각 모듈이 대략 무엇을 담당하는지
- 이후 기능을 수정하려면 어떤 파일을 우선 확인해야 하는지

6. 후속 수정 위험
- 어떤 파일이나 디렉터리의 수정 위험이 높은지
- 어떤 로직을 함부로 수정하면 안 되는지
- 전역 스타일, 전역 설정, 인증, API, 데이터베이스 등 고위험 영역이 있는지
- 후속 수정 시 특히 주의해야 할 점은 무엇인지

프로젝트 이해 보고서만 출력하고 코드는 수정하지 마세요.
출력이 끝나면 제 확인을 기다려 주세요.
