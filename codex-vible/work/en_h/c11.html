Part 4: The standard workflow

From requirement to delivery, end to end

Many people start using Codex by giving it a single sentence:

Help me build a website. Help me change this feature. Help me optimize this project.

This can work, but it often leaves one problem: AI changes things quickly, but you may not know exactly what changed or whether it is safe to deliver.

A more reliable way is to avoid changing everything at once and move through a fixed workflow.

The idea is:

A requirement does not turn directly into a deliverable. It must go through these steps: understanding, planning, changing, verifying, checking, and accepting.

The standard six-step method

Step Name In simple terms Purpose
1 Break down requirements First make sure Codex understands the kind of project it is working on Avoid changing code blindly without understanding the structure
2 Make a plan List what needs to be done, then start after confirmation Avoid changing too much at once or moving in the wrong direction
3 Implement in small steps Change only a small piece at a time Reduce the chance of errors and make rollback easier
4 Test Run checks and verify manually after changes Confirm the code has no obvious errors
5 Code review Review the diff and check whether the changes are correct and safe Prevent AI from changing places it should not touch
6 Commit and review Commit the code and record what you learned AI executes; people make the final call
Step 1: Break down requirements

Before asking Codex to modify a project, start by breaking down the requirement instead of writing code.

Many people run into trouble with Codex because the requirement was unclear at the start, not because Codex cannot write code.

For example, if you only say:

Help me optimize the homepage.

Codex may understand it as:

  • Change the UI
  • Change the copy
  • Change the layout
  • Change the component structure
  • Change routing
  • It may even delete code that it considers "unused" along the way.

Before formal work begins, break the requirement into several core questions.

What is the background?

First explain why this task needs to be done.

Question Example
What stage is the project in now? This is an official website page that is already online
What is happening now? The homepage conversion rate is low, and users do not understand the product's selling points
Why change it now? A new version is about to be released, so the above-the-fold messaging needs improvement
What type of requirement is this? UI optimization / Bug fix / New feature / Refactor
What problem needs to be solved?

The requirement should be as specific as possible. Do not just write "optimize," "make it prettier," or "make it better."

Vague wording Clearer wording
Optimize the homepage Optimize the homepage hero title, subtitle, and CTA button
The page does not look good Adjust card spacing, font hierarchy, and button styles
Login has a problem Fix the issue where clicking the login button does not redirect
Build an admin dashboard Add a user list page with search, filters, and pagination

A good requirement should answer:

What specific problem are we solving this time?

Example:

This time, mainly solve three problems:
1. The hero title is not clear
2. The CTA button is not obvious
3. The mobile hero content is too crowded
Which files may be related?

If you roughly know where the files are, it is best to tell Codex in advance.

This reduces the chance that it searches and changes files randomly across the whole project.

Scenario Possibly related files
Change the homepage app/page.tsx, pages/index.tsx, components/Hero.tsx
Change styles globals.css, tailwind.config.js, related component files
Change login login/page.tsx, auth.ts, middleware.ts
Change APIs api directory, server directory, lib directory
Change copy Page components, config files, i18n files
Which features must not be touched?

This matters.

Codex may change other areas while completing the current task.

Tell it in advance:

Content that must not be touched Explanation
Login logic Only change the UI; do not change the authentication flow
API addresses Do not change API request paths
Data structure Do not change database fields
Route structure Do not change existing page paths
Existing components Do not perform large refactors unless necessary
Dependency versions Do not upgrade or add dependencies casually

This step draws boundaries for Codex.

What result counts as done?

Do not just say "finish it." Tell Codex what "done" means.

Requirement type Completion standard
UI optimization The page looks noticeably better, and mobile is not broken
Bug fix The original error disappears, and related features work normally
New feature Users can complete the full operation flow
Performance optimization The build succeeds, and page loading is not noticeably slower
Copy optimization The title, subtitle, and button copy are clear

Example:

Completion criteria:
1. The homepage hero clearly communicates what the product is for
2. The CTA button is more obvious
3. Mobile display is normal
4. Other pages are not affected
5. The project can run and build normally
What tests are needed?

After changes, do not rely only on Codex saying "done." Explain in advance how to verify the result.

Test type Applicable scenario
Page preview UI changes, page layout adjustments
Console check Frontend pages and interactive features
Build test Next.js, React, and Vue projects
Unit tests Projects with test files
Manual flow testing Flows such as login, payment, forms, and upload
Mobile testing Responsive pages, product cover images, and mobile web pages
What risks are there?

When breaking down requirements, ask Codex to assess risks in advance.

This helps prevent random fixes while it changes code.

Risk Explanation
Scope is too large A small requirement turns into a large refactor
Style pollution Global CSS is changed and affects other pages
Dependency risk Unnecessary dependencies are added, making the project more complex
Logic risk Fixing one issue breaks other flows
Data risk Changes touch APIs, fields, or database-related content
Compatibility risk Desktop works, but mobile breaks
Requirement breakdown prompt template

When using Codex, you can copy this directly:

Please help me break down the requirement first. Do not modify code immediately.

Requirement:
[describe your requirement here]

Please analyze it with the following structure:

1. What is the background?
- What is the current project roughly about?
- Why does this requirement need to be done?
- Is this requirement a new feature, bug fix, UI optimization, or refactor?

2. What problem needs to be solved?
- What is the specific current problem?
- To what extent should this be solved this time?
- What is outside the scope this time?

3. Which files may be related?
- Please judge which files may be involved based on the project structure
- List them first; do not modify them directly

4. Which features must not be touched?
- Which logic should not be changed?
- Which APIs should not be touched?
- Which pages or components should not be affected?

5. What result counts as done?
- Feature completion criteria
- Page completion criteria
- Code completion criteria

6. What tests are needed?
- What commands need to be run?
- Which pages need manual checking?
- Which flows need focused verification?

7. What risks are there?
- Which features may be affected?
- Is there a risk of style pollution?
- Is there a risk of over-refactoring?
- Is there a risk of adding dependencies?

Finally, give me a short execution recommendation:
- Which step do you recommend doing first?
- Do you need my confirmation before modifying anything?
Step 2: Let Codex make a plan

After the requirement breakdown is complete, do not ask Codex to start writing code right away.

In this step, ask Codex to make a plan first.

The idea is:

First have AI explain how it plans to do the work. Then decide whether it should start.

Many projects go wrong because Codex starts changing things immediately, not because it cannot make the change.

By the time you notice the direction is wrong, it may already have changed many files, making review and rollback hard.

The core of the second step is:

Plan first, execute later. Confirm first, modify later.

Do not write code yet

Put this at the very beginning of the prompt.

Codex's default tendency is to solve the problem immediately after seeing the requirement.

In real projects, changing code directly is risky.

Problem with writing code directly Possible consequence
The project structure is not understood The wrong file is changed
The requirement boundaries are not confirmed Features outside the requirement are built
The impact scope is not assessed Existing features are damaged
The test method is not listed You do not know how to verify the changes after they are made
Too much is changed at once Rollback is hard after an error

Example prompt:

Do not write code yet, and do not modify any files.
Please make a modification plan first based on the current requirement and project structure.
Wait for my confirmation before starting implementation.
Turn on Plan mode

You can refer to the "Plan mode" section in the earlier basic Codex App usage chapter. In actual use, you can also type /plan directly in Codex CLI or App, let Codex output a plan first, and then decide whether to execute it.

Step 3: Implement in small steps

Enter the code modification phase only after the plan is confirmed.

One principle matters here:

Do not let Codex change everything at once.

Many people run into trouble with Codex because they ask it to "implement everything" at the start.

It may then change pages, components, styles, APIs, and configuration at the same time. The project may look different, but it becomes hard to tell where a problem came from.

A more reliable way is:

Change only one feature point at a time. After each small step, check that step.

Change one feature point at a time

Small-step implementation depends on controlling the change scope.

For example, if you want to optimize the homepage, do not ask for everything at once:

Please help me optimize the entire homepage.

Split it like this instead:

Step Change
Step 1 Only optimize the hero title and subtitle
Step 2 Only adjust the CTA button
Step 3 Only optimize the mobile layout
Step 4 Only add product selling-point cards
Step 5 Only handle final style details

This keeps each step clear and makes problems easier to locate.

Do not let Codex refactor unrelated code

Codex sometimes decides that code is "not clean enough" and tries to refactor it while doing the task.

In real projects, extra refactoring is dangerous.

What Codex may try to do Possible problem
Rename components Causes import paths to break
Split files Increases maintenance cost
Change global styles Affects other pages
Optimize old logic Breaks features that were originally working
Upgrade dependencies Creates compatibility problems
Delete code it thinks is unused The code may actually be business logic

During small-step implementation, set clear limits:

This time, implement only the current feature point.
Do not refactor unrelated code along the way.
Do not change names, directory structure, dependency versions, or global configuration.
If you find code that could be improved, record it as a suggestion first. Do not modify it directly.

This sentence is very important.

Codex can make suggestions, but it must not expand the change scope on its own.

Do not accept large unexplained changes

If Codex changes many files at once without a clear explanation, pause.

Be especially careful in these situations:

Situation How to handle it
The number of changed files suddenly becomes large Ask it to explain why each file was changed
A large amount of code was deleted Ask it to explain why it was deleted
An unfamiliar dependency was added Ask it to explain why it is necessary
A configuration file was modified Ask it to explain the scope of impact
A page unrelated to the requirement was changed Ask it to revert the unrelated change
The code style changed a lot Ask it to keep the original project style
When uncertain, stop and ask first

Small-step implementation does not mean Codex should ask about everything. It means Codex must stop when there is critical uncertainty.

For example:

Uncertain situation Why stop?
Not sure which file to change Prevents changing the wrong place
Not sure about business rules Prevents implementing the wrong logic
Not sure whether old code can be deleted Prevents deleting features by mistake
Not sure whether to add a dependency Prevents making the project more complex
Not sure what an API means Prevents affecting data
Not sure why a test failed Prevents fixes from creating more confusion

You can add this rule to Codex in advance:

If you encounter any of the following situations, stop and ask me first. Do not decide on your own:

1. You are not sure which file to change
2. You are not sure whether to delete old code
3. You are not sure whether to add a dependency
4. You are not sure how to handle the business logic
5. You are not sure why a test failed
6. You find that changes beyond the original plan are needed
Small-step implementation prompt template

In practice, you can copy the following directly:

Please start small-step implementation.

For now, execute only step [1]:
[describe the single feature to build this time]

Requirements:
1. Change only this feature point at a time
2. Modify only files directly related to the current feature
3. Do not refactor unrelated code along the way
4. Do not change the directory structure
5. Do not add unnecessary dependencies
6. Do not delete existing features
7. Do not change files outside the plan

After finishing the change, please stop and output:

1. Which files were changed this time
2. What changed in each file
3. Why these changes are necessary
4. Whether anything outside the plan was changed
5. Whether there are potential risks
6. What you recommend doing next

Note:
If you encounter anything uncertain, stop and ask me first. Do not decide on your own.
Step 4: Test

After Codex completes a small-step change, do not move to the next step immediately. Test first.

The biggest problem many people have with Codex is this:

AI says it is done, but the project does not actually run. The page looks normal, but some features are already broken. The current feature is fixed, but old features are affected.

The core of testing is: do not trust Codex when it says "done"; use results to prove that the work is actually done.

The following table covers a complete test pass. Run checks from fastest to slowest:

Test type Purpose Common commands Focus
Unit tests Check whether functions, components, and modules work correctly npm test / pnpm test / yarn test If they fail, explain the reason first; do not directly change code
Type check Find type errors early in TypeScript projects npm run typecheck / tsc --noEmit If there is no such command, say so clearly
lint Check code quality issues (unused variables, import order, Hook usage, etc.) npm run lint Separate newly introduced issues from existing project issues
Build Opening locally does not mean the project can ship; the build proves it can be packaged npm run build / pnpm build If it fails, first summarize the error and impact scope
Manual testing UI, forms, login, payment, and upload require manual clicking through None Verify each step along the user operation path
Browser testing Page, console, and API problems that cannot be seen in the terminal None Check page display, Console errors, Network, and mobile layout
Regression testing Test the new feature and check whether old features were broken None List old pages and components that may be affected by this change

Two reminders: many old projects already have lint or type issues, so do not let Codex refactor all historical issues while it works. Beginners often miss regression testing; even changing a homepage button may affect other pages that reuse the same component.

During manual testing, you can ask Codex to list the verification steps as an "action and expected result" table, for example:

Step Action Expected result
1 Open the homepage The page loads normally
2 Click the CTA button It redirects to the registration page
3 Shrink to mobile width The page does not deform
4 Open the console There are no obvious red errors in the console
Testing-stage prompt template

In practice, you can copy this directly:

Please test this change. Do not continue adding features.

Please execute or explain in the following order:

1. Unit tests
- Does the project have unit tests?
- If yes, run the test command
- If they fail, explain why

2. Type check
- Does the project have a typecheck command?
- If yes, run it
- If not, say so

3. lint
- Run lint checks
- Separate newly introduced issues from existing project issues

4. Build
- Run the build command
- If it fails, explain the error reason and impact scope

5. Manual testing
- List pages that need manual testing
- List user operation steps
- List the expected result for each step

6. Browser testing
- Check page display
- Check console errors
- Check mobile layout
- Check key buttons and interactions

7. Regression testing
- Check whether this change affects old features
- List pages, components, and flows that may be affected

Finally, output a test summary:
- Which tests passed
- Which tests failed
- What caused the failures
- Whether we can move to the next step
- Whether issues need to be fixed first
Step 5: Code review

Passing tests does not mean the change is ready to deliver.

You still need a code review.

Use code review to check this:

Do not just check whether the code runs. Check whether the changes are correct, stable, and safe.

Codex writes code quickly, but these problems can still appear:

Common problem Explanation
The feature runs, but the logic is wrong It looks normal on the surface, but the real business flow has problems
The change is too large Many unrelated pieces of code are changed for a small requirement
Old logic is deleted by mistake Code that looks unused but is actually useful is deleted
Edge cases are ignored Normal input works, but abnormal input crashes
Security issues Secrets are exposed, permission checks are wrong, or input is not validated
Style is inconsistent New code does not match the existing project style
Maintainability is poor Temporary hard-coding makes later changes harder

Code review is not optional. It is a core step in the Codex workflow.

Two review rounds: Codex self-review + human review

For the first round, ask Codex to self-check the changes it just made. The goal is not to trust it completely, but to make obvious problems visible first. Ask it to output a table:

Check item Result Explanation
Were files outside the plan changed? No Only homepage-related components were modified
Were dependencies added? No package.json was not modified
Was old logic deleted? No The original button redirect logic was kept
Are there risks? Yes Mobile button spacing still needs human confirmation

The second round is human review. You, not Codex, are responsible for delivery. You do not need to understand every line, but focus on these parts of the diff:

Review focus What to check
File scope Whether only the files that should be changed were changed
Changed / deleted content Whether it matches the plan and whether old features were deleted
Names and structure Whether they match the original project style
Business logic Whether it matches the real requirement (runs ≠ correct logic)
Test results Whether tests were actually run

For important code involving login, payment, permissions, databases, authentication, and similar areas, consider using a second model for cross-review. One model writes, and another model focuses on finding problems. This is usually unnecessary for copy-only changes or minor styles. Do not accept the second model's suggestions wholesale either. It helps find problems; it does not make the final decision for you.

Focus on four high-risk problem types

Codex is most likely to go wrong in these four areas, so review them closely:

Category Common problem Review focus
Edge cases Normal input works, abnormal input crashes Empty data, API failure, not logged in, insufficient permissions, mobile sizes, repeated clicks
Security issues When users / APIs / permissions / payments / uploads / databases are involved Whether secret tokens are exposed, whether permission checks are missing, whether input is validated, whether sensitive information is leaked, whether APIs have authentication
Accidental deletion Code that seems useless but is actually useful is deleted Focus on deleted content in the diff; old components, comments, compatibility code, fallbacks, and config items may still be in use
Business logic The code runs but the logic is wrong (wrong page redirect, wrong price calculation, privilege escalation) Normal paths, abnormal paths, permission checks, and whether old business rules were overwritten

If you see a large deletion without a clear explanation from Codex, do not accept it directly.

Code review prompt template

In practice, you can copy this directly:

Please do a code review for this change. Do not continue writing code.

Please review using the following structure:

1. Codex self-review
- Did this change only modify files inside the plan?
- Is there unrelated refactoring?
- Were dependencies added?
- Is there hard-coding?
- Was old logic deleted by mistake?

2. Change scope review
- Which files were changed?
- Why was each file changed?
- Are there changes outside the plan?
- Are there large unexplained changes?

3. Edge case review
- How is empty data handled?
- How are API failures handled?
- How are unauthenticated users handled?
- How are insufficient permissions handled?
- How are repeated clicks handled?
- Could mobile behave abnormally?

4. Security issue review
- Are secrets, tokens, account names, or passwords exposed?
- Are permission checks affected?
- Is input validation missing?
- Could sensitive information be leaked?
- Was API authentication logic modified?

5. Deleted content review
- Which code was deleted?
- What is the reason for deletion?
- Is it confirmed that nothing else depends on it?
- Could it affect old features?

6. Business logic review
- Does it meet the requirement?
- Is the normal flow correct?
- Is the abnormal flow correct?
- Does it affect old business rules?
- Are there uncertain business assumptions?

7. Review conclusion
Finally, give a conclusion:
- Can continue
- Needs small fixes
- Needs partial rollback
- Needs a new plan

Note:
Only review. Do not continue modifying code.
If you find problems, explain the problems and suggestions first, then wait for my confirmation before changing anything.
Step 6: Commit and review

After the code passes testing and review, the final step is not simply saying "done."

A complete Codex workflow also needs two things:

First, formally commit this change. Second, capture what was learned from this change.

Many people use Codex only until "the code runs," then skip commit notes, PR descriptions, problem records, and documentation updates.

That may look fine in the short term, but over time it creates a problem:

Every time feels like the first time. Every time needs to be explained again. Every time repeats the same mistakes.

So the core of the sixth step is:

Delivery does not end the workflow. Review makes the next change easier.

Generate a commit

After this change has passed testing and review, you can ask Codex to generate a commit.

A commit should not be a vague "update." It should explain what changed this time.

A good commit should answer:

Question Explanation
What changed? The main content of this commit
Why was it changed? Which requirement or problem it corresponds to
What is affected? Which modules, pages, or features are involved
Did tests pass? Whether build, lint, and tests passed

Common commit message formats:

feat: add user profile page
fix: resolve login redirect issue
style: improve homepage responsive layout
refactor: simplify product card component
docs: update setup guide

For a localized project, you can also write the description in the team's working language:

feat: add user profile page
fix: fix abnormal redirect after login
style: optimize the homepage mobile layout
docs: update project usage instructions
Write a PR

If the project uses GitHub, GitLab, or a team collaboration flow, write a PR after committing.

A PR is not a formality. It lets others quickly understand:

What the PR should explain Purpose
What was done this time Helps the reviewer understand quickly
Why it was done Explains the requirement background
Which areas changed Reduces review cost
How it was tested Shows the change was deliberate
What risks there are Exposes uncertainties in advance
What needs focused review Guides the reviewer's focus

A good PR description can look like this:

## Changes in this PR

- Optimize the homepage hero title, subtitle, and CTA button
- Adjust the mobile hero layout
- Keep the original redirect logic; APIs and routes were not modified

## Test results

- npm run lint passed
- npm run build passed
- Manually checked homepage display on desktop and mobile
- CTA button redirect works normally

## Risk notes

- This change involves homepage style adjustments, so mobile display needs focused confirmation
- No dependencies were added
- Login, API, and database logic were not modified
Record problems

During review, record problems encountered in this process.

This step is very important.

In the Codex workflow, the main value is not "this time is done," but this:

The next time you encounter a similar problem, you can avoid the same detours.

Problems that need to be recorded include:

Problem type Example
Requirement problem The initial requirement description was not clear enough
Planning problem Codex missed mobile in the plan
Change problem Codex changed an unrelated component along the way
Testing problem The project does not have a typecheck command
Review problem It was found to have deleted fallback logic by mistake
Communication problem The prompt did not clearly say "do not add dependencies"

The record format can be simple:

Problem record for this change:

1. Problem: Codex initially wanted to modify global styles
   Reason: The requirement did not clearly limit the scope to “only change the homepage”
   Solution: Add to the prompt that only homepage-related files should be modified

2. Problem: Mobile testing was missed
   Reason: The planning stage did not list mobile acceptance criteria
   Solution: Always add mobile checks to the test checklist in the future

3. Problem: The PR description was not clear enough
   Reason: Test results were not recorded in advance
   Solution: Generate a test summary immediately after each test run
Summarize prompts

If the prompts used this time worked well, save them.

The purpose of this step is simple:

Do not rewrite useful prompts every time.

For example, suppose you found this sentence useful:

Do not refactor unrelated code along the way.
If you find that changes beyond the plan are needed, stop and ask me first.

Record it and use it as a fixed rule in the future.

You can organize it as a table:

Effective Prompt Applicable scenario Why it works
Do not write code yet; make a plan first All complex requirements Prevents Codex from making random changes directly
Change only one feature point at a time Multi-step tasks Reduces error and rollback cost
Do not refactor unrelated code along the way Maintaining old projects Prevents the change scope from expanding
Summarize the diff after changes are done After every change Makes human review easier
When uncertain, stop and ask first When business logic is unclear Prevents AI from making decisions on its own
Update AGENTS.md

If certain rules need to be followed every time in the future, do not keep them only in chat. It is better to update the project-level AGENTS.md.

AGENTS.md can be understood as:

A project rulebook written for Codex.

It can tell Codex:

Content Purpose
How the project runs Tells Codex the start, test, and build commands
What the code style is Prevents code that does not match the project style
Which directories must not be touched Prevents accidental changes to core files
What to do before changing code Sets "plan first, execute later" as a rule
What the testing requirements are Defines which checks must be run after changes
What the commit requirements are Defines how commits and PRs should be written

Example content:

# AGENTS.md

## Working rules

- Before changing anything, read the project structure first.
- Before changing anything, make a plan first. Do not write code directly.
- Implement only one feature point at a time.
- Do not refactor unrelated code along the way.
- Do not add unnecessary dependencies.
- When business logic is uncertain, ask first. Do not decide on your own.

## Testing requirements

After each change, check at least:

- npm run lint
- npm run build
- Manual testing for related pages
- Whether the browser console has errors
- Whether the mobile layout is normal

## Commit requirements

Before committing, explain:

- Which files were changed
- What changed in each file
- Whether tests passed
- Whether there are risks or unfinished items
Update project documentation

Besides AGENTS.md, if this change affects how the project is used, update the project documentation too.

For example:

Change Documentation to update
New feature README, feature guide
New environment variable .env.example, deployment docs
New command README, development guide
API changed API docs
Deployment flow changed Deployment guide
Configuration changed Configuration guide
New component Component usage guide

Documentation is updated to avoid forgetting details later, not to make the project look better.

Common documentation includes:

File Purpose
README.md Project introduction, startup method, common commands
.env.example Environment variable examples
docs/ Detailed project documentation
CHANGELOG.md Version update record
AGENTS.md Codex working rules
CONTRIBUTING.md Team collaboration guidelines
