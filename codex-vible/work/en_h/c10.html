Code management (Git and GitHub workflows)

When you use Codex on real projects, you need a basic understanding of Git and GitHub.

For beginners, start with this:

Git = a local code version-management tool
GitHub = a platform for putting code online and collaborating
Codex = an AI programming assistant that helps you read code, edit code, and run commands

In one sentence, it works like this:

Git records code changes.
GitHub handles remote storage and collaboration.
Codex helps you complete specific programming tasks.

Difference between Git and GitHub

Comparison Git GitHub
Simply put A local version management tool A code cloud drive + collaboration platform
Main purpose Records what changed in the code each time Stores code remotely and supports team collaboration
Where it is used On your computer In the browser / cloud
Core features commit, branch, diff, merge repository, issue, pull request
Requires internet? No Yes
Relationship with Codex After Codex edits code, use Git to inspect and save it Codex Web / Cloud often works together with GitHub

Git Worktree

Open another independent working copy for the same Git project.

Think of it as a scratchpad. When the result is ready, merge it back into the official project.

Why Worktree is needed

Ordinary Git branches can be switched, but one folder can use only one branch at a time.

Worktree helps in these cases:

Scenario What Worktree does
You want Codex to try risky code changes Give it a separate copy
You do not want to affect the current project Keep the main project unchanged
You want to work on multiple tasks at the same time Use one worktree for each task
You want to compare multiple solutions Keep options A / B / C separate
A change is broken and you do not want it Delete the worktree
You are making large changes / refactoring Reduce the risk of affecting the main project
Create a Worktree

Use a branch for a task

Merge back to the main line

After you check the result, merge it back to the main line and delete this branch if you no longer need it.

Running in the cloud

Codex cloud tasks are useful when you cannot keep your local computer running. If your account and client support mobile access, you can also check some tasks or move them forward while you are away.

Give code tasks to Codex and let it run them by itself in a cloud environment.

Before making local changes, sync the latest code from the GitHub repository

If a cloud task has already pushed changes back to GitHub, sync the latest code before continuing local development. This avoids editing an old version and creating conflicts. Whether Codex automatically applies the changes for you, or you manually run git pull / codex apply, depends on the current entry point and task type.

A project rulebook written for Codex.

For beginners, think of it this way:

File Main reader Purpose

Where to put AGENTS.md
Location Scope Simply put
AGENTS.md in the project root The whole project The overall rules for the current project
AGENTS.md in a subdirectory The current subdirectory and related tasks Dedicated rules for a specific module
User-level ~/.codex/AGENTS.md All your projects Personal general rules
Project-level AGENTS.md + user-level AGENTS.md Applied together Personal habits + current project rules
How to write AGENTS.md

You can give the project to AI and ask it to summarize the core rules in an AGENTS.md file.

Frontend project AGENTS.md template
# AGENTS.md

## Project description

This is a frontend web project used to build product pages, tool pages, or personal portfolio pages.

## Tech stack

- React
- Vite
- Tailwind CSS
- JavaScript / TypeScript

## Common commands

- Install dependencies: `npm install`
- Start the project: `npm run dev`
- Build the project: `npm run build`

## Project structure

- `src/`: main source code
- `src/components/`: shared components
- `src/pages/`: page files
- `src/assets/`: static assets such as images and icons
- `public/`: public static files

## Code conventions

- Prefer React function components
- Prefer Tailwind CSS for styling
- Do not introduce Bootstrap
- Do not refactor unrelated code on a large scale
- Keep the file structure clear when editing
- Interface copy should be natural, concise, and suitable for ordinary users

## UI rules

- Pages should have a clear information hierarchy
- Buttons, cards, headings, and spacing should be consistent
- Mobile should be basically usable
- Do not overuse gradients, shadows, or an AI-template feel
- Prioritize a real product feel rather than a demo feel

## Prohibited actions

- Do not modify `.env` or `.env.local`
- Do not output API keys, tokens, or passwords
- Do not delete existing core features
- Do not add large dependencies casually
- Do not directly modify files unrelated to the current task

## After completing a task

After each change is complete, output:

1. Which files were modified
2. What changed in each file
3. Why these changes were made
4. Whether `npm run build` needs to be run
5. Remind me to check the diff
What makes a good AGENTS.md
Characteristic Description
Specific Lists the tech stack, commands, and directories clearly
Concise Stays short
Actionable Codex can tell what to do after reading it
Has limits Names the files that must not be touched
Has validation Names the command to run for checks
Has completion criteria Lets Codex know what to deliver
Maintainable Updated when the project changes

Global-level AGENTS.md

Open Codex settings and find personalization

Enter instructions here. They act as your personal general preferences and affect later Codex sessions

When using AI for programming, a common worry is that AI may delete things carelessly. You can use these instructions.

Do not delete files or directories in batches.

Do not use:

  • del /s
  • rd /s
  • rmdir /s
  • Remove-Item -Recurse
  • rm -rf

When you delete files, delete only one file at one explicit path at a time.

Correct example:

Remove-Item "C:\path\to\file.txt"

If files need to be deleted in batches, stop the operation and ask the user to delete them manually.
